Setup

Installation

SemiUI is copied into your project through a CLI, not installed as a compiled dependency. No Tailwind setup is assumed — bring whatever styling approach your app already uses.
Angular 22+ Standalone components & the new control-flow syntax
Any styling setup Plain CSS works out of the box. Tailwind is optional and never required
@ng-icons/core Only needed once you add a component whose preset references an icon
Step by step

From npx to a working component

1

Initialize SemiUI

Scaffolds components.json, asks which preset to start from (Semi by default, or any of the other six -- see the full preset catalog), and installs the theme engine, primitives, and the chosen preset package. Skip the prompt entirely with --preset <name>. Run it from the root of an Angular project — a angular.json must already exist there.

npx @semiui/cli init

2

Wire up the theme provider

Every copied component reads its colors, spacing and radius from the active preset. Add the provider once and it applies to every component you add afterward.
src/app/app.config.ts 
import {{ '{' }} provideSemiUI {{ '}' }} from '@semiui/theme';
import {{ '{' }} Semi, provideSemiIcons {{ '}' }} from '@semiui/presets-semi';

export const appConfig: ApplicationConfig = {{ '{' }}
  providers: [
    // ...your existing providers
    provideSemiUI({{ '{' }} preset: Semi {{ '}' }}),
    provideSemiIcons(),
  ],
{{ '}' }};
3

Add your first component

This copies the component's real source — not a compiled bundle — into src/app/components by default. It's yours from the moment it lands: edit it, break it, delete parts you don't need.
Terminal 
npx semiui add button

# Done. ButtonComponent is now yours to edit.
4

Use the component

Import it with a relative path, like any other file in your project — because that's exactly what it is now.
booking-card.component.ts 
import {{ '{' }} ButtonComponent {{ '}' }} from '../components/button/button.component';

  selector: 'app-booking-card',
  imports: [ButtonComponent],
  template: `<s-button variant="primary" (pressed)="confirm()">Confirm</s-button>`,
{{ '}' }})

{{ '}' }}

Staying up to date

The files are yours, so a new SemiUI release can't reach in and change them — but you shouldn't have to delete and re-copy a component to pick up a fix either. semiui add records what it wrote in semiui.lock.json: the release each file came from, and a hash of its contents. Commit that file. It's what lets the CLI tell a component you've customised from one you never touched.

Terminal 
npx semiui update

select
  select.component.html              updated
  select.component.css               updated
  select.component.ts                merged with your edits

button
  button.component.ts                left alone -- you edited it, nothing new upstream
Untouched files Overwritten outright. That's most of them, and it's the boring case that used to cost you an afternoon.
Files you've customised Three-way merged against the exact release you installed from, so library changes land around your edits instead of on top of them.
Genuine collisions You get ordinary <<<<<<< conflict markers in the one region that needs a human, and a non-zero exit code for CI.

Run semiui diff first to see what's waiting without touching anything, or semiui update --dry-run to see exactly which files would be rewritten, merged, or left alone. Already have components from before the lockfile existed? Run semiui update once — anything still matching a shipped recipe gets adopted automatically, and the rest is reported rather than guessed at.

That's the whole workflow

init once, add as many components as you need, and every one of them is a plain file in your own repo from the moment it lands — with semiui update to pull library changes in later without losing what you changed. Back to overview
