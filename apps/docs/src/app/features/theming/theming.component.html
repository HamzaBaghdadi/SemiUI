Shape

What a preset actually is

Every preset — built-in or your own — is a plain object satisfying ThemePreset. No class, no build plugin.
theme-preset.ts 
interface ThemePreset {{ '{' }}
  name: string;
  primitive: PrimitiveTokens;    // raw values -- blue.500, slate.200, white, night.base
  semantic: SemanticTokens;      // meanings -- primary, destructive, muted, spacing, radius, typography
  components: ComponentTokens;   // one entry per component -- button, input, tag...
  dark?: ThemeOverrides;         // dark-mode overrides, normally semantic tokens only
  icons: IconTokens;             // logical slot -> icon reference
{{ '}' }}
Three layers

How a token resolves

A preset never names a CSS variable. It writes {{ '{' }}token.path{{ '}' }} references, and the engine follows them — which is what makes one override reach every component downstream of it.

Those swatches come from resolvePresetToken() reading the real Semi preset, not from values typed into this page. The generated CSS keeps the chain intact rather than flattening it — --semiui-color-primary is literally var(--semiui-primitive-blue-500) — which is why redefining three variables under .dark is enough to move the whole library.

What a token value can be

The system is deliberately not all-or-nothing. Reuse a token when the value has design-system meaning; keep it raw when it is genuinely local to one component.

Disabled state

Opacity or colors — your call

Disabled means "this component, dimmed" everywhere: each component's *Disabled colors point back at its own live colors, and one semantic opacity.disabled (generated as --semiui-opacity-disabled) does the fading. No component hard-codes its own dimming — and if you would rather grey a component out than fade it, repoint its colors and set its opacityDisabled to 100%.
definePreset(Semi, ...) 
// "Disabled" has two independent levers, and every component that has the state
// exposes both. Pick either, or use them together.

// 1. Opacity. One semantic token; every component's own opacityDisabled points at it,
//    so this one line changes how faded "disabled" is across the whole library.
semantic: {{ '{' }} opacity: {{ '{' }} disabled: '40%' {{ '}' }} {{ '}' }}

// 2. Colors. Each component's own *Disabled surface tokens.
components: {{ '{' }}
  input: {{ '{' }}
    // Semi dims a disabled field -- it stays itself, just faded. Repoint these
    // and turn the dimming off to grey the field out instead.
    backgroundDisabled: '{{ '{' }}muted{{ '}' }}',
    foregroundDisabled: '{{ '{' }}mutedForeground{{ '}' }}',
    opacityDisabled: '100%',
  {{ '}' }},
{{ '}' }}
Custom presets

Writing your own

A preset is just data — spread an existing one and override only what changes. Pass the result to provideSemiUI in place of Semi or Aurora, the same call from step 2 of the installation guide.
src/app/presets/ember.preset.ts 
import {{ '{' }} Semi {{ '}' }} from '@semiui/presets-semi';
import {{ '{' }} definePreset {{ '}' }} from '@semiui/tokens';

export const Ember = definePreset(Semi, {{ '{' }}
  name: 'ember',
  primitive: {{ '{' }}
    ember: {{ '{' }}
      50: '#fffaf5', 100: '#ffedd5', 200: '#fed7aa',
      400: '#fb923c', 500: '#ea580c', 800: '#9a3412', 900: '#431407',
    {{ '}' }},
  {{ '}' }},
  semantic: {{ '{' }}
    primary: '{{ '{' }}ember.500{{ '}' }}',
    background: '{{ '{' }}ember.50{{ '}' }}',
    foreground: '{{ '{' }}ember.900{{ '}' }}',
    muted: '{{ '{' }}ember.100{{ '}' }}',
    mutedForeground: '{{ '{' }}ember.800{{ '}' }}',
    border: '{{ '{' }}ember.200{{ '}' }}',
  {{ '}' }},
  dark: {{ '{' }}
    semantic: {{ '{' }} primary: '{{ '{' }}ember.400{{ '}' }}' {{ '}' }},
  {{ '}' }},
{{ '}' }});
// Nothing else needs saying: every component token references the semantic layer, so
// buttons, tags, focus rings and checked checkboxes all follow automatically.
src/app/app.config.ts 
import {{ '{' }} provideSemiUI {{ '}' }} from '@semiui/theme';
import {{ '{' }} Ember {{ '}' }} from './presets/ember.preset';

export const appConfig: ApplicationConfig = {{ '{' }}
  providers: [
    // ...your existing providers
    provideSemiUI({{ '{' }} preset: Ember {{ '}' }}),
  ],
{{ '}' }};

Presets build on presets

definePreset merges key by key at every depth, so overriding blue.500 keeps the other ten shades and overriding one button variant keeps the other nine. It never mutates the base, and the result can itself be extended.

Dark mode

Where the dark palette comes from

A preset's semantic tokens are its light-mode values; its dark block re-points just the handful of them that change. Component tokens reference the semantic layer, so they follow on their own — no parallel dark component tree. provideSemiUI writes both onto a single <style> tag — the base tokens on :root, the dark palette scoped under .dark — so the cascade handles switching, not JavaScript. It also installs ColorModeService, which toggles that class, persists the choice to localStorage, and falls back to the OS preference. This is exactly what the moon icon in this site's top bar calls.
topbar.component.ts 
import {{ '{' }} ColorModeService {{ '}' }} from '@semiui/theme';

@Component({{ '{' }} /* ... */ {{ '}' }})
export class TopbarComponent {{ '{' }}
  protected readonly colorModeService = inject(ColorModeService);
{{ '}' }}

// template: (click)="colorModeService.toggle()"
Optional

Bridging into Tailwind

If your project already uses Tailwind v4, install the bridge -- a plain CSS file, copied into your project like any other component -- and Tailwind utilities like bg-primary, text-muted-foreground, rounded-md, bg-blue-500 and p-semiui-md automatically follow whichever preset and light/dark mode is active -- on plain Tailwind-classed elements, not just SemiUI's own components. Opacity modifiers (bg-primary/10) and aliases (bg-danger) work too, and no dark: variant is needed for a semantic color.
Terminal 
npx semiui add tailwind
Then import it after Tailwind itself in your global stylesheet -- order matters, since the bridge's values need to win the cascade for anything your own @theme block also defines:
src/styles.css 
@import "tailwindcss";
@import "./tailwind/tailwind.css"; /* wherever "semiui add" placed it -- after @import "tailwindcss" */
The bridge is generated from the preset's token tree, not hand-written, so a semantic token added to a preset becomes a Tailwind utility with no extra work. Component tokens are deliberately left out: components.button.variants.primary.background stays internal. Spacing and typography arrive namespaced (p-semiui-md, text-semiui-sm). Tailwind resolves max-w-*, w-* and h-* named keys through its --spacing-* scale as a fallback, so claiming a bare --spacing-xl would silently rewrite max-w-xl from 36rem to 1.5rem. Colors and radius are never namespaced -- bg-primary and rounded-md following the preset is the point.

Generated, not hand-written

The bridge is produced from the preset's token tree by @semiui/tailwind, which holds no list of colors and no --semiui-* string of its own — it walks the tokens and asks the engine for each variable name. Customizing a color from Tailwind's own palette

A preset's color fields are plain CSS color strings -- point one at your own Tailwind theme's palette directly (PrimeNG-style theming, e.g. "primary is green-500") instead of a literal hex:
my-preset.ts 
const MyTheme = definePreset(Semi, {{ '{' }}
  name: 'my-theme',
  semantic: {{ '{' }}
    primary: 'var(--color-green-500)',        // <- your own Tailwind theme's green-500
    primaryForeground: 'var(--color-white)',
  {{ '}' }},
{{ '}' }});
